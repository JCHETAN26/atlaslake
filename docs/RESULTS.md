## Baseline vs AtlasLake (Phase 42)

Working scale: **10m** events. Every cell is copied from the JSON files below by `benchmarks/report.py`.

| Metric | Baseline (Phase 4) | AtlasLake |
|---|---|---|
| Data freshness (event → queryable) | ≥ 27.6 s after each run *plus* the schedule interval (full refresh) | p50 22.5 s / p95 38.9 s (continuous) |
| Throughput | 162,521 source rows/s — recomputes from *current state*; consumes no events, keeps no history | 29,625.3 events/s historical drain (validate, dedup, Bronze + DLQ + Silver) · 6,344.6 events/s sustained live (bounded by the single-process source workload) |
| Processing runtime (whole history) | 26.1 s | 321.0 s stream drain |
| Backfill runtime | 26.1 s (only option: full refresh) | 507.4 s for 9,514,989 records, 41 weekly chunks; rerun changes nothing: ✅ yes |
| Duplicate correctness | not applicable: reads source *state*, cannot consume an event stream | 950,951 injected → 0 leaked |
| Recovery from crash | re-run from scratch (26.1 s at this scale) | 52.5 s after restart; lost 0, duplicates 0 |
| Query p50 (median across the 6 queries) | 39.50 ms | 2.20 ms |
| Query p95 (worst query) | 289.70 ms | 20.80 ms |
| Same answers on every query |  | ✅ yes |

**How to read this.** The baseline is a full refresh of *current source state*. At small scale it is cheap, but it has no event history (no SCD2, no replay), its freshness is bounded by its schedule, it cannot absorb duplicate, late or invalid *events*, and its cost grows with total history on every run (see the scale ladder below). AtlasLake processes each event once, incrementally, through validation, dedup and an immutable Bronze record; its per-event work is higher, and that buys the correctness rows of this table.
