# Security (Phase 33)

The goal is that every component gets the minimum access it needs, data is encrypted at rest and
in transit, secrets never live in git or images, and the Gold analytics layer exposes no raw PII.

## Data classification

| Field(s) | Class | Where it may appear |
|---|---|---|
| `email`, `phone` | **restricted** | Postgres source, Kafka payloads, Bronze (raw bytes), `silver.customers` / `silver.customer_changes` |
| `first_name`, `last_name` | **confidential** | same as above |
| `city`, `state`, `country`, `segment` | internal | everywhere, including Gold (needed for SCD2 analysis) |
| order / payment / inventory facts | internal | everywhere |
| `email_masked` (`o***@example.com`) | confidential (derived) | Gold `dim_customer` |

These rules are enforced in code:

- **dbt staging is the PII boundary.** `stg_customer_changes` emits only `{{ mask_email('email') }}`.
  Phone and names never leave Silver. Gold `dim_customer` has no raw PII, and the baseline pipeline
  drops the same columns.
- PII-bearing Silver columns carry `COMMENT 'PII: restricted|confidential'` in their Iceberg DDL
  (`spark/common/tables.py`), and the Avro contracts carry a `doc` with the same label.
- **Logs never print payloads.** DLQ records keep the raw bytes in the DLQ table (access-controlled
  like Bronze). Logs contain only ids, counts and error codes.
- In Snowflake, a tag-based masking policy (`snowflake/02_masking.sql`) masks any column tagged
  `PII_CLASS = restricted|confidential` for every role except `ATLAS_PII_READER`. That's defence in
  depth on top of the masking already done in Gold.

## Identity and access (least privilege)

**AWS** (`infrastructure/terraform/modules/compute`):

- The ECS **execution role** can pull images, write its own log groups, and read one Secrets
  Manager secret (the DB credentials), plus `kms:Decrypt` on the project CMK. Nothing else.
- The ECS **task role** has S3 `Get/Put/Delete` only on the `bronze/`, `silver/`, `gold/` and
  `warehouse/` prefixes of the lake bucket. `ListBucket` is conditioned on the same prefixes. It
  also has KMS on the one CMK and `GetSecretValue` on the one secret. `cloudwatch:PutMetricData` is
  conditioned to namespace `AtlasLake`. MSK permissions, when enabled, are scoped to `commerce.*`
  topics and the cluster's groups.
- The trust policy for both roles is limited to `ecs-tasks.amazonaws.com`, with an `aws:SourceArn`
  condition for this account and region.

**Postgres** (`docker/postgres/init/00_databases.sql`, `sql/source_schema.sql`):

| Role | Can |
|---|---|
| `commerce_app` | DML (SELECT/INSERT/UPDATE) on `commerce.*`. This is the workload generator. |
| `etl_reader` | SELECT on `commerce.*`; read/write on `ops.*` (relay checkpoint, delivery log) |
| `analyst` | Read-only on the `analytics` DB (baseline marts, no PII) |
| `marquez`, `airflow` | Own only their own databases |
| `atlas` | Bootstrap superuser for the local stack only. In AWS the master secret is used for migrations only. |

**Snowflake** (`snowflake/01_setup.sql`): `ATLAS_LOADER` (service user, key-pair auth, writes
STAGING and merges into GOLD), `ATLAS_TRANSFORMER` (owns GOLD objects), `ATLAS_ANALYST` (SELECT on
GOLD, sees masked values) and `ATLAS_PII_READER` (unmasked, granted sparingly). Schemas use
**managed access**, so grants are central, and future grants keep new tables governed. A resource
monitor suspends the warehouse at the monthly credit cap.

## Encryption

- **At rest:**
  - The S3 lake uses SSE-KMS with a customer-managed key (rotation on, S3 Bucket Keys on). The
    bucket policy denies `PutObject` without `aws:kms`.
  - RDS storage, Secrets Manager, CloudWatch log groups, SNS and ECR repositories are all encrypted
    with the same CMK.
  - Locally, MinIO data lives on the developer's disk. It's synthetic data only.
- **In transit:**
  - The S3 bucket policy denies any request with `aws:SecureTransport = false`.
  - The RDS parameter group sets `rds.force_ssl = 1`.
  - MSK Serverless is TLS-only, with IAM authentication.
  - Snowflake connections are always TLS.
  - The local docker-compose stack uses plaintext on a private Docker network bound to localhost.
    That's acceptable for synthetic dev data and documented here as a local-only exception.

## Secrets management

- **Local:** configuration comes from `ATLAS_*` environment variables with dev-only defaults
  (`core/config.py`). Overrides go in `.env`, which is git-ignored, and `.env.example` documents the
  keys with no real values.
- **AWS:** the RDS master password is generated by Terraform (`random_password`), stored only in
  Secrets Manager (KMS-encrypted), and injected into tasks through the ECS `secrets` field. It never
  appears in a task definition, an image or the logs. Terraform state contains the password, so the
  remote state bucket must be encrypted and access-restricted (see the backend block in
  `versions.tf`).
- **Snowflake:** the service user authenticates with an RSA key pair held in Secrets Manager or a
  local file. There's no password.
- **CI** holds no cloud credentials and runs only `terraform validate`.

## Network isolation

- All subnets are private, and nothing in the stack has a public IP. RDS is `publicly_accessible = false`.
- There's no NAT gateway. S3 traffic uses a gateway endpoint, and ECR, logs, Secrets Manager, KMS,
  STS and CloudWatch use interface endpoints.
- Security groups:
  - **ECS tasks:** no inbound rules. Outbound is only 443, plus 5432 to the RDS security group and
    9092–9098 inside the VPC.
  - **RDS:** inbound 5432 only from the ECS security group.
  - **MSK:** inbound only from the ECS security group.
